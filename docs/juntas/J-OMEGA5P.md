#### (b) Serviço de ocupação transacional que PROVA I1 (1-para-1 vaga×processo sob concorrência)
I1 tem **duas metades**, cada uma com garantia de banco distinta (belt-and-suspenders):
- **I1b "um processo ≤ 1 vaga"** ⇒ **partial-unique** `(tenant_id, current_process_id) WHERE NOT NULL`. Duas tx que estacionam o MESMO `processId` em vagas diferentes travam vagas diferentes (sem contenção de lock); o 2º commit viola o índice → **P2002 → 409 `PROCESS_ALREADY_PARKED`**. Garantia do DB, não da app.
- **I1a "uma vaga ≤ 1 processo"** ⇒ **lock de linha + guarda de status na MESMA tx** (`withTenantRls`→`$transaction`): `SELECT ... FROM yard_spots WHERE tenant_id=$1 AND id=$2 FOR UPDATE` serializa concorrentes na MESMA vaga; a 2ª tx bloqueia, re-lê `status='OCCUPIED'` e recebe **409 `SPOT_NOT_FREE`**. (A coluna única já impede 2 processos na mesma linha; o `FOR UPDATE` fecha a janela check-then-write.)

`OccupancyService` (métodos service-level, exercitados por teste em PR-01; wire ao processo real = PR-06):
- `allocate(actor,{spotId,processId})`: tx RLS → lock `FOR UPDATE` → exige `FREE` (senão 409) → `SET status='OCCUPIED', current_process_id=$pid` (P2002→409). *(match `vehicle_class` vaga×veículo = deferido PR-06, precisa do impound.)*
- `vacate(actor,{spotId})`: lock `FOR UPDATE` → exige `OCCUPIED` → `SET status='FREE', current_process_id=NULL`.
- `move(actor,{fromSpotId,toSpotId})`: 1 tx; trava as 2 vagas `FOR UPDATE` em ordem determinística (min(id),max(id)) anti-deadlock; exige `from=OCCUPIED`/`to=FREE`; **limpa `from` ANTES de setar `to`** (senão o partial-unique dispara no meio); preserva o `processId`. Primitivo de **RN-PAT-02**; a transferência ENTRE pátios completa (evento `TRANSFERIDO_PATIO` + `CustodyEvent` preservando o processo) = **deferida ao PR-06/impound**.
- Bloqueio operacional (`FREE⇄BLOCKED`) = transição de status simples sob `yard:update` (sem processo).
- **InMemory** espelha a lógica 1:1; a prova de RACE real (Postgres `FOR UPDATE` + partial-unique) roda no teste DB-gated (Node é single-thread → InMemory prova a LÓGICA dos guards, não a corrida).

#### (b) Cadeia de hash (I2) — canonicalização determinística + função de hash + verificação que DETECTA adulteração
**O coração probatório do PR.** Módulo dedicado `src/modules/impound/impound.hashchain.ts` (funções PURAS, `node:crypto`, ZERO dependência nova — canonical-json NÃO existe no repo e lib nova exige junta-de-5).

**1. Canonicalização determinística `canonicalJson(value): string`** — serializador próprio, NÃO `JSON.stringify` cru (ordem de chaves de objeto não é semanticamente estável):
- objetos: chaves ordenadas por **code point** (`Array.sort()` sobre as chaves), recursivo; sem espaços; `{"a":1,"b":2}`.
- arrays: ordem preservada (ordem É semântica).
- strings: via `JSON.stringify` (escapa aspas/controle — inclusive `\u001e`, ver separador abaixo).
- números: **inteiros apenas**; o validator REJEITA número não-finito ou não-inteiro no payload (422 `non_canonical_number`). **Dinheiro/km NUNCA são number** — vão como **string** (`"12.50"`), coerente com o invariante Decimal(12,2)/(10,1). Fecha o furo de `0.1+0.2`/`1.0`→`"1"`.
- `null` permitido; `undefined`/função → rejeitado (422). Determinismo total, testável por property-based.

**2. Preimage + hash `computeEventHash(input): string`** — a fórmula do prompt `sha256(prev_hash + canonicalJson(payload) + occurred_at + actor_id)`, **endurecida contra injeção de fronteira e reordenação**:
```
SEP        = "\u001e"   // RECORD SEPARATOR (0x1E): NUNCA aparece em hash hex, UUID, ISO-8601, nem em JSON (é escapado como \u001e)
GENESIS(t,p) = sha256hex("SIGPRV-CUSTODY-GENESIS-v1" + SEP + t + SEP + p)  // ancora a cadeia AO processo (anti-enxerto cross-process)
preimage   = prev_hash + SEP + String(seq) + SEP + type + SEP + canonicalJson(payload) + SEP + occurred_at.toISOString() + SEP + (actor_id ?? "\u0000")
hash       = sha256hex(preimage)
```
- **`seq` no preimage** ⇒ reordenar 2 eventos muda o hash (anti-reorder), além do encadeamento por `prev_hash`.
- **`SEP` reservado** ⇒ o `canonicalJson(payload)` (que pode ter texto arbitrário) não consegue "vazar" p/ o campo seguinte: um `\u001e` literal no texto vira `\u001e` (6 chars ASCII) no JSON, nunca o byte 0x1E. Fecha o ataque de **canonical-json injection** (deslocar fronteira de campo).
- **`GENESIS` amarrado a `tenant_id`+`process_id`** ⇒ uma subcadeia válida do processo A, replantada sob B, quebra logo no seq=1 (`prev_hash` esperado ≠). Anti-enxerto.
- **`actor_id` sentinela `\u0000`** quando null (sistema) ⇒ hash determinístico sem ambiguidade null×"".

**3. Verificação `verifyChain(events, {tenantId, processId, head})` — GET `/impound-processes/:id/verify`** (sob `impound:read`): carrega TODOS os eventos por `seq ASC` e recomputa do zero:
- `expectedPrev = GENESIS(tenantId, processId)`; `expectedSeq = 1`.
- por evento: (i) `seq === expectedSeq`? senão **`seq_gap`** (faltando/inserido/reordenado); (ii) `prev_hash === expectedPrev`? senão **`prev_hash_mismatch`** (elo quebrado/enxerto); (iii) `computeEventHash(evento) === hash`? senão **`hash_mismatch`** (payload/occurred_at/actor/type/seq adulterados); então `expectedPrev = hash`, `expectedSeq++`.
- ao fim, confronta a **âncora do agregado**: `count === process.custody_seq_head`? e `expectedPrev === process.custody_hash_head`? senão **`head_mismatch`**/**`count_mismatch`** — **detecta DELETE da ponta** (apagar o último evento não muda os anteriores, mas a âncora no `impound_processes` [mantida na mesma tx do append] denuncia).
- resposta: `{ processId, valid, eventCount, headHash, brokenAt?: {seq, reason}, checkedAt }`. Determinística, sem PII (só hashes/seq).

**4. Anti-forge de DB-write (endurecimento sobre I2, HONESTO quanto ao modelo de ameaça):** hash-chain é **tamper-EVIDENT**, não tamper-PROOF contra adversário com escrita irrestrita no banco que **recompute toda a cadeia + a âncora**. Contramedida barata reusando a casa: **cada append grava TAMBÉM um `AuditLog` (tabela append-only INDEPENDENTE) com `metadata:{processId, seq, hash}`** (sem PII). Forjar passa a exigir adulterar **dois** stores auditados independentes na mesma janela. Âncora externa forte (Sivec outbox/notarização) = Ω6 (D-Ω5P-05). *Declaro o modelo de ameaça à junta explicitamente — o `critico-adversarial` vai atacar exatamente isto.*

**5. Append transacional `appendEvent(tx, {process, type, payload, occurredAt, actorId})`** (privado do serviço, base de TODA escrita): dentro de `withTenantRls`→`$transaction`: (i) `SELECT … FROM impound_processes WHERE tenant_id=$1 AND id=$2 FOR UPDATE` (serializa appends concorrentes no MESMO processo — anti-corrida da FSM); (ii) `seq = custody_seq_head + 1`; `prev_hash = custody_hash_head ?? GENESIS`; (iii) `hash = computeEventHash(...)`; (iv) `INSERT custody_events` (a `@@unique(tenant,process,seq)` é o backstop: 2 tx que passem do lock por caminhos distintos → P2002 → 409 `concurrent_custody_append`); (v) `UPDATE impound_processes SET custody_seq_head=seq, custody_hash_head=hash`; (vi) `AuditLog`. Tudo 1 tx atômica.

#### (b) Desenho FORMAL do motor (ESTUDO §5) — `charging.accrual.ts` (PURO, testável por DI, zero I/O)
Sejam `t0 = entered_at`, `T_stop = frozen_at`, `asOf = min(now, T_stop)`, `TZ = yard.timezone`. **DST-safe sem lib nova:** aritmética de calendário via `Intl.DateTimeFormat({ timeZone: TZ })` (ICU embutido no Node — dependência ZERO; lib de data exigiria junta-5). ROLLING usa tempo físico absoluto (imune a DST por definição — 24h são 24h em ms); CALENDAR e o teto de 6 meses usam data-local-do-pátio via Intl.
- **`n_diárias(asOf)` — ESTUDO §5 `min( ⌈(min(t,T_stop)−t0)/24h⌉ , cap(perfil,t0) )`, reconciliado:**
  - **ROLLING_24H** (federal, art.21 §1º): a diária **N vence em `t0 + N·24h`** (1ª em `t0+24h` — a convenção EXPLÍCITA do ESTUDO §5). Operacionalmente = `nDue = floor( (asOf − t0) / 24h )`; períodos `1..nDue` são devidos. **Reconciliação honesta do teto `⌈·⌉`:** a notação-teto do ESTUDO conflita com "1ª vence em t0+24h" (teto daria 1 diária já em t0+ε); adoto a **convenção parentética (piso; nada devido em `[t0, t0+24h)`)** como fonte de verdade, e deixo `firstDailyAtEntry` como flag de perfil **DEFERIDA** (o ESTUDO diz "parametrizável se o perfil público local dispuser diferente"). O **property-test da fronteira** trava exatamente `asOf=t0+24h−1s → 0` e `asOf=t0+24h → 1`.
  - **CALENDAR** (contratual): `nDue = #{datas-locais distintas em [t0, asOf]}` no TZ do pátio (entra 23:30 dia D, às 00:10 do dia D+1 → 2 diárias). DST-safe por extrair Y-M-D locais via Intl.
- **Teto intertemporal (I4 / RN-DIA-02), aplicado pela DATA DE ENTRADA via `profile.daily_cap`** (o perfil é escolhido na abertura refletindo o regime de `t0` — ESTUDO §2.3):
  - `SIX_MONTHS` (art.271 §10 / 328 §5º): `capDate = t0 + 6 meses de calendário` (no TZ do pátio, via Intl — 6 meses ≠ 180 dias); `cap = n_diárias(capDate)` sob o MESMO modelo. Acumulação **PARA** no teto.
  - `THIRTY_DAYS_LEGACY` (Tema 124/STJ): `cap = 30` (contagem fixa).
  - `UNLIMITED` (privado): sem teto.
  - `nAccrue = min(nDue, cap)`.
- **Congelamento (RN-DIA-04):** `asOf = min(now, frozen_at)`. O motor recebe `asOf` explícito → a transição que seta `frozen_at` (liberação PR-10 / arrematação PR-14) chama `accrueProcess(process, asOf=frozen_at)` UMA vez para fechar o período final; depois disso o sweep ignora o processo (`frozen_at NOT NULL`). Sob ROLLING um período final parcial (<24h) = 0 diária extra (piso); sob CALENDAR o dia do congelamento conta.
- **Valor unitário — `resolveTariff` FAIL-CLOSED (F7 do PR-03):** por refDate de cada diária a acumular, `resolveTariff({ tenantId, serviceCatalogId: profile.daily_service_catalog_id, scope: profile.scope (PUBLIC_AGREEMENT|PRIVATE_CONTRACT), vehicleCategory: undefined, date: refDate })`. **`undefined` ⇒ NÃO cria diária com amount 0 em silêncio:** o processo é marcado `error_count++` no run, log `warn` sem PII, e a diária fica **não-acumulada** (o próximo run tenta de novo; publicada a tarifa vigente para aquela data, o **catch-up** acumula as faltantes). `profile.daily_service_catalog_id = NULL` ⇒ mesmo fail-closed. **`vehicleCategory: undefined`** porque `ImpoundProcess` não tem coluna de categoria normalizada — só as passadas curinga (∅) do `resolveTariff` rodam; se o tenant só tiver tabela categoria-específica → `undefined` → fail-closed (comportamento F7 correto). Categoria-no-preço = aditivo DEFERIDO (coluna futura em `impound_processes`).
- **Recalculabilidade (RN-DIA-05 / I2):** o job **só CRIA diárias faltantes** (idempotente); **nunca reprecifica** uma diária já acumulada. Tarifa corrigida a posteriori ⇒ **ADJUSTMENT** (novo lançamento), nunca UPDATE. Cada diária resolve a tarifa vigente **na SUA refDate** (não no relógio de parede) — o `resolveTariff` já passa `date` como `asOf` (F1 do PR-03).
- **Backfill/catch-up:** por processo, o motor computa o conjunto de refDates devidas em `[t0, asOf]` (capado) e cria as `ProcessCharge DAILY` **AUSENTES** (idempotência pelo partial-unique). Worker caído não pula diária; latência ≠ correção.

  - `computeNotificationSchedule(t0, profile) → DueMark[]`: OWNER_INITIAL em `t0 + ownerNotifDays*24h`, COMPLEMENTARY_EDICT em `t0 + noticeEdictDay*24h` (tempo ABSOLUTO, DST-imune, coerente com o rolling-24h do §5), **ordenados por `due_at`**. **AUCTION_EDICT NAO é agendado aqui** (é relativo à DATA do leilão, >=15 dias úteis — PR-13); declarado no enum para os PRs donos, aditivo-friendly (espelha os subtipos de leilão já declarados em `CUSTODY_EVENT_TYPES`).
  - `isNotificationTrailComplete(profile, notifications) → boolean` — **o predicado de I6 que PR-12/13 importam**: só `true` quando os kinds EXIGÍVEIS do perfil estão ISSUED (ou WAIVED com `reason`); `false` se algum DUE/ausente. Puro, sem I/O (mesma filosofia de `summarizeAccrual`).
- **Sweep `impound.notify-due` (`impound.notifications.sweep.service.ts` + `.jobs.ts`, espelha `charging.accrue-daily` linha a linha):** auto-reenfileirante (delay fixo 1h), `getDefaultJobQueue().enqueue`, gated por `JOBS_WORKER_ENABLED` (default OFF ⇒ CI/testes nunca sobem o loop), ator = **SISTEMA** (fora do RBAC HTTP), reenfileira no `finally` (catch-up). Por tenant ATIVO (try/catch por tenant — um tenant que lança não derruba a varredura): candidatos = `entered_at IS NOT NULL AND frozen_at IS NULL AND status NOT IN ('JUDICIAL_HOLD')` **E** `profile.scope='PUBLIC_AGREEMENT'` (privado NAO roda o rito administrativo — `resolveDefaults` comenta). Para cada `DueMark` com `due_at <= now` ainda não materializada (checa `(tenant,process,kind)` sob o lock; partial-unique é o backstop): INSERT DUE + `appendNotificationEventTx` na MESMA tx. **Idempotente** (não dupla; re-run/catch-up após queda do worker materializa quando `now >= due_at` — latência != correção). **Fail-closed:** scope!=público → pula; prazo ausente/<=0 → pula o marco + `logger.warn` (sem PII), **jamais fabrica data**. **Congelamento/suspensão da régua:** `frozen_at` (RELEASED/AUCTIONED/DIRECT_RECYCLING→CLOSED) já sai por `frozen_at IS NULL`; `JUDICIAL_HOLD` (§§14-15) suspende explicitamente; marcos já materializados **persistem** (append-only) mesmo se depois liberado — é a trilha probatória.
- Registro: `JOB_NAMES` (+`"impound.notify-due"`), `job.registry.ts` (+register do handler), `src/server.ts` (+`enqueueInitialImpoundNotifyDueScan()` sob o gate, `server.ts:20-34`) — **tudo aditivo, espelhando `charging.accrue-daily`**.

#### (d) I6 como invariante — o que garante + como PR-12/13 consomem
**I6 (ESTUDO §4.3):** *nenhum lote é consumado sem trilha de notificação íntegra* (inicial <=10d + edital >=30d acessível >=10d + edital de leilão >=15 d.u.). PR-09 **materializa a TRILHA de forma AUDITÁVEL**: (i) `ProcessNotification` (quando DEVIDA, quando emitida, meio, destinatário minimizado, status); (ii) cada marco/emissão é um `CustodyEvent NOTIFICATION` **hash-encadeado + cross-anchor** — a trilha é *tamper-evident* (adulteração → `verifyChain` quebra); (iii) `isNotificationTrailComplete` = o predicado puro da pré-condição. **A APLICAÇAO do bloqueio** (impedir AUCTION_PREP→LOTTED→AUCTIONED sem trilha completa) é da **FASE 4**: PR-12/13 trocam a guarda `deferred` das arestas de leilão (`impound.transitions.ts:119-128`) pela guarda REAL que chama `isNotificationTrailComplete(profile, notifications)` + confere `verifyChain.valid` — aditivo, sem tocar a FSM. PR-09 entrega os dados + o predicado; a Fase 4 acopla. O edital do leilão (>=15 d.u.) e a janela "acessível >=10 dias" são verificados no gate de leilão (relativos à data do certame), não em PR-09 (R5).
